### R1-F1 — INVALID_PARAMS error echoes are not capped (P3, static, pre-existing sites, gap vs. new invariant)

- Location: `crates/code-reality/src/mcp_server.rs:447-451` (`files` element echo), `:601-605` (`algorithm`), `:640-644` (`detail_level`), `:843-847` (`producer`).
- Causal path: a client sends a tools/call with an oversized invalid parameter → the rejection message interpolates the caller-controlled string verbatim (`format!(... 收到：{other}，...)`) into `McpError::new` without `apply_text_cap` → unbounded error text reaches transport serialization. The round-1 cap (`internal_error`, mcp_server.rs:236-238) covers every INTERNAL_ERROR construction site (tool exit, join failure, panic, data-plane module error — verified exhaustively by grep: 7 `internal_error` sites, 4 remaining `McpError::new` sites are these echoes), but INVALID_PARAMS sites were not converted.
- Relation to obligations: these four sites predate the remediation and were not in R0-02's reproduced path (uncapped *tool output*). However, EP invariant 2 states "Error and success text follow the same UTF-8-safe bounded payload rule" without restricting it to one error code, so this is an honest coverage gap against the stated invariant rather than a regression.
- Evidence strength: static source read; not executed. Risk is bounded by the local-stdio trust model (the client must itself deliver the oversized parameter first).
- Suggested validation: real-stdio probe — `tools/call build` with `producer` = 2 MB string; assert response message ≤ cap + marker.

### R1-F2 — Idle reader busy-poll at ~500 Hz per live backend (P3, static, introduced)

- Location: `crates/code-reality-lsp-bridge/src/transport.rs:100-108` (`Pipe::read` loops on `WouldBlock` with `TICK = 2ms`, reader deadline `None` at `:197-201`); same-shape 2–5 ms polls in `Writer::send` (`:37-47`) and `lock_until` (`session.rs:343-362`).
- Causal path: stdout is set nonblocking (`:159`), so the reader thread never blocks in `read(2)`; while the backend is alive but silent, the thread wakes every 2 ms forever. Sessions live for the bridge process lifetime (lazy spawn, `Drop`-terminated), so a resident bridge with warm backends pays a permanent wake-up tax (order 0.1–0.5 % of a core per backend; not measured — this is a mechanism-derived estimate, not a benchmark).
- Relation to obligations: introduced by the R0-05 transport rewrite; correctness is unaffected (this is what makes the threads joinable), but the cost is undisclosed — bridge README documents "nonblocking stdin" but no polling cost.
- Evidence strength: static mechanism read; no runtime measurement.
- Suggested validation: spawn one pyrefly session, keep idle 60 s, sample CPU (`ps -o %cpu`); if material, add read-poll backoff or a self-pipe/wakeup channel.

### R1-F3 — Reader head-of-line blocking on server-request replies is bounded but only indirectly tested (P3→observation, static, introduced)

- Location: `crates/code-reality-lsp-bridge/src/transport.rs:213-221` — server→client requests are answered through the same bounded writer queue with a fixed `Instant::now() + 30s` deadline.
- Causal path: writer queue (capacity 8) full because the writer thread is blocked writing a large frame to a stalled child → reader thread enters `reply_writer.send` and spins up to 30 s → during that window the reader delivers no responses, diagnostics, or replies, so an unrelated in-flight request can only end via its own deadline (which terminates the session per contract). A single failed reply exits the reader loop (`:220-221`), correctly session-terminal under the accepted "every transport timeout invalidates the session" rule.
- Relation to obligations: the design decision ("reader replies use same writer path") was accepted in ep.md R0-05; the `flood-client` regression proves bounded *shutdown* under exactly this backpressure, but response-latency degradation for a concurrent caller is not separately exercised. I consider this within-contract behavior worth recording, not a defect; the 30 s constant is also not tied to any session deadline (bounded by construction).
- Suggested validation (optional): during `flood-client`, run a concurrent hover and assert it fails by its own entry-based deadline without external rescue.
