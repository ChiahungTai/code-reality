## Root CR advisory

### Verified key facts (evidence base)

1. **The failure is rust-analyzer's, relayed by CR.** CR's rust leg hands the repo *directory* to `rust-analyzer scip` (`~/Github/code-reality/crates/code-reality/src/build.rs:385-391`); rust-analyzer's `ProjectManifest::discover_single` scans the root and its *immediate children* for `Cargo.toml`, finds `rust/` + `dutymail/`, and bails `more than one project`; CR relays stderr as `BuildError::Env` → exit 2 (`build.rs:398-404`).
2. **Option (b) as hypothesized does not exist.** CR offers no layout hint for the rust leg — no `--project`, no include paths; `.code-reality.toml` `exclude` explicitly does NOT reach the Rust leg (`engine.rs:511-515`, recorded exemption); and `rust-project.json` is **not** a linkedProjects list — it is a full project model (per-crate roots/deps/cfg/env), while `linkedProjects` is a client-side LSP setting the `scip` CLI never reads. Worse: rust-analyzer discovery honors a `rust-project.json` found in the dir **and its parents**, so one planted at the root would hijack every rust-analyzer consumer of this repo — the per-subworkspace CR builds, the user's editor, and `code-reality-lsp-bridge` (the Stage-1 working face in `docs/staleness-policy.md`).
3. **The root face worked before dutymail existed.** `.code-reality/scip/index.scip.meta.json` (stamped 2026-10-03, one day before the dutymail EP `00-tasks/2026-10/10-04-dutymail/ep.md`) shows a healthy root build: faces `python, rust, javascript`, producers `pyrefly-index 0.9.5 / rust-analyzer 1.96.0 / scip-typescript 0.4.0`. The root graph is stale, not impossible — the second workspace is the sole regression.
4. **CR already contains the composition primitive.** `concat_scip` (`build.rs:192-199`, protobuf same-type cat-merge) merges producer parts, and `merge_and_publish` (`build.rs:432-466`) already merges across language families into one slot/graph.db; graph.db builds are greenfield + atomic-rename; `indexed_source_identity` is content-only and root-independent (`identity.rs:3-7, 271-315`, TC-1a pins different-roots-same-content → same identity). Snapshot's `assert_git_root` (`snapshot.rs:304-329`) is the only root-anchoring gate, and it passes at the repo root.
5. **DB-80 workspace separation is mechanically load-bearing, not ceremonial.** Three deliberate divergences are only expressible with separate workspace roots: (i) release profiles — rust/ mandates `lto=true, panic="abort"` (crash-only, `rust/Cargo.toml:18-22`) while dutymail is `opt-level=s, strip` only (`dutymail/Cargo.toml:32-34`), and `lto`/`panic` cannot be overridden per-package on stable cargo; (ii) lock discipline — dutymail builds are strictly `--locked` against a committed lockfile that `sync-version` member-patches (`scripts/lib/version-sites.mjs:49-55, 192-209`), rust builds never `--locked` (`scripts/assemble-release.mjs:83` vs `:97`) — one lockfile couples every rust dependency bump into a dutymail re-lock; (iii) version/feature isolation — the two lockfiles today intentionally diverge in minors (libc 0.2.189/0.2.190, thiserror 2.0.20/2.0.21, uuid 1.26.1/1.27.0). The boundary is machine-enforced by `tests/contract/workspace-boundary.test.mjs` gates A–D, and the EP freezes it: "Reopening repository placement… or weakening the four boundary gates requires a new decision" (`ep.md:16`); the A1 amendment explicitly preserved "source-level separation… enforced at the source/dependency level, not by distribution" (`ep.md:24`).

### 1. Position

**Option (c): keep both workspaces; add a multi-root compose mode to code-reality** (run one rust leg per nested workspace root, cat-merge the scip parts with the existing `concat_scip` primitive, build one root-anchored graph.db, stamp root identity/HEAD — auto-detecting nested workspace roots). This is the only option that fixes the *cause* (a single-project discovery assumption in the graph tool) without paying with *architecture*: the repo's two-workspace layout is a frozen DB-80 decision whose separation is mechanically load-bearing (profiles, lock discipline, version/feature isolation — fact 5), and CR is a tool the user owns and actively versions, so the fix lands where the defect lives. It also restores exactly what the repo had before dutymail landed — a root-anchored, three-language graph covering `rust/`, `dutymail/`, **and** the Node/Python tooling that no subworkspace graph covers (fact 3) — and it generalizes: a future third workspace re-breaks nothing. Option (a) buys the same root coverage with zero tool changes but only by overturning a standing decision and erasing three real separations to save a feature-add in the user's own tool; option (b) as written rests on a mechanism that does not exist, and its salvageable variant (a generated rust-project.json) silently hijacks every rust-analyzer consumer and can drift stale *while freshness stays green* — poison for a trust tool; option (d) keeps the root faces the user already ruled unreasonable.

### 2. Concrete implementation sketch

All code changes live in **code-reality** (`~/Github/code-reality`, currently 0.9.5 at HEAD 25fd932); nothing in delegate-bridge changes except deleting stale derived state.

1. **Multi-root discovery in the rust leg** — `crates/code-reality/src/build.rs` `stage_rust` (`:374-407`): when the repo dir itself has no `Cargo.toml`, enumerate immediate child dirs containing one (this is exactly rust-analyzer's own child-scan — the current failure condition becomes the trigger). One child → today's single-run path; N children → spawn `rust-analyzer scip <child-dir> --output <part-i>` once per root (same `current_dir` pinning, `:382-391`); zero → current error. Each part keeps the existing `<128`-byte empty-index guard (`:212-221`).
2. **Part merge** — reuse `concat_scip` (`build.rs:192-199`) on the N rust parts before `merge_and_publish` (`:432-466`), exactly as language families already merge; the producer string lists each root (e.g. `rust-analyzer 1.96.0 ×2 roots`).
3. **Identity/freshness: no semantic change.** `ProductionIdentity::capture` hashes per-rel-path corpus bytes of the face, and the rust-face walk already covers the whole repo tree (skipping only `target/`, `engine.rs:670-675`) — the union corpus is what it already sees; HEAD stamping is unchanged. Verify `scip_refs --stamp-meta` shares this harvest path (the stale root slot was stamped by `scip_refs`, meta `"tool": "code_reality.scip_refs"`) so both faces get the fix.
4. **Snapshot/delta_tour: no change.** `assert_git_root` passes at the repo root; composed graph.db absolute paths under both subtrees resolve via `repo_relative`; `_meta` anchoring is unchanged.
5. **delegate-bridge side (housekeeping only):** `rm -rf .code-reality/` at the repo root (gitignored derived data — `*` in its `.gitignore` — containing the stale pre-dutymail graph/slot/snapshot); then `code-reality build --repo .` from root. Optionally note the restored root face in `docs/staleness-policy.md`.
6. **Interim (optional, until the CR release carries compose):** formalize the option-(d) router — a two-line wrapper that runs `freshness`/`snapshot` per `rust/.code-reality` and `dutymail/.code-reality` — so structural claims route correctly during the gap.

No `.code-reality.toml` config is needed; auto-discovery self-maintains as workspaces change (a `--rust-root` repeatable override can be added for explicitness, but auto should be the default).

### 3. Blast radius

- **delegate-bridge: zero source/build/release/test changes.** No manifest, script, SOP, or contract-lane edits — this is the decisive contrast with option (a), whose mechanical change list spans `scripts/lib/version-sites.mjs`, `assemble-release.mjs`, `writer-preflight.mjs`, `package.json:12-13`, `carrier-canary.sh:36`, `dutymail/scripts/release-local.sh:60-64`, a rewrite of `workspace-boundary.test.mjs` gates A–C, root `.gitignore`, and every documented `rust/target/release/delegate-bridge` entry path (root `AGENTS.md:23,187,230`; `docs/build-loop.md:21`; `docs/runbook.md:87-96`), plus profile reconciliation and silent-breakage hazards (root `target/` unignored; stale binaries at old paths; parity-test byte drift on a re-profiled dutymail leaf).
- **code-reality: one feature, contained.** `build.rs` discovery + merge, multi-root tests (two nested workspace fixtures), version bump, reinstall `~/.cargo/bin/code-reality`. The bridge's review attach calls `graph_query detect_changes` — unaffected by discovery changes; the staleness-policy "probe by use" discipline (`docs/staleness-policy.md:85-99`) covers the CLI-upgrade step anyway.
- **Coverage restored beyond the status quo ante:** root graph re-covers `scripts/`, `tests/`, and python tooling via the js/py legs — which no per-subworkspace graph can ever cover.
- **Cost:** one full root build ≈ both rust legs + js/py legs; the ~8-minute figure for the old single-workspace root face (`docs/staleness-policy.md:31-47`) is the anchor — remeasure in place per that policy's own rule; cadence stays low-frequency by design.

### 4. Guard for the no-path-dep boundary

Option (c) does **not** weaken workspace isolation — both workspaces stay byte-identical to DB-80's frozen shape, and the existing machine guard (Gate A exact-four-members, Gate B `cargo metadata` canonical cross-path-dep rejection in `tests/contract/workspace-boundary.test.mjs:268-280, 390-402`) remains in force and green. A bonus becomes available: the composed graph is itself boundary evidence — with zero sanctioned cross-workspace code contact (subprocess-only, `dutymail/AGENTS.md:248-249`), cross-graph edges should be identically zero, and any edge crossing the `rust/`⇄`dutymail/` divide in the graph would be a structural alarm that could later be asserted in the boundary lane as a third, evidence-level gate.

### 5. Risks and what I could not verify

- **scip cat-merge collisions:** graph.db keys `nodes.symbol UNIQUE` with `INSERT OR IGNORE` (`graph_db.rs:799-816`) — two rust indexes whose symbol spaces are crate-qualified (bridge-* vs dutymail-*) make collisions unlikely, but a collision would drop a node silently; needs a dedicated multi-root test in CR (assert node count = sum minus known-shared external symbols).
- **Could not execute anything** (read-only advisory): did not reproduce the failure, did not run `rust-analyzer scip`, did not measure compose cost. rust-analyzer discovery semantics were verified against CR source plus upstream *master* (`project-model/src/lib.rs`); the installed binary is 1.96.0 (root meta producer line) — minor drift between master and 1.96.0 tag is possible.
- **Producer-path coverage:** the stale root slot was stamped via `scip_refs --stamp-meta`, not `build` — I could not fully confirm every stamping face shares the same harvest entry point; the sketch flags this as the first thing to check.
- **js/py legs at root today:** they passed on 2026-10-03; current-tree behavior (`.mjs` handling by scip-typescript 0.4.0, pyrefly over `dutymail/scripts/rehearsal-m3.py`) unverified.
- **Cross-workspace semantics of derived views:** communities/flows are computed per greenfield build; whether a stitched two-component graph renders sanely in `arch_overview`/`communities` is untested (two disconnected components is the *correct* picture, but UX is unproven).

### 6. Strongest counter-argument, and why it does not win

**"You are fixing a delegate-bridge problem by modifying a different product. Option (a) needs zero tool changes and one decision; DB-80's real end — no code coupling — survives a merge via a rewritten metadata-based boundary test (assert no dutymail⇄bridge crate deps inside the one workspace); the no-backward-compatibility standing direction invites exactly this kind of one-time restructuring; and a single root workspace also simplifies the IDE."** This is the honest strength of (a), and it would win if CR were a third-party tool or if workspace separation were mere ceremony. It does not win because all three premises fail here: CR is the user's own actively-versioned tool (0.9.5, its own staleness policy, its own lsp-bridge), so "modifying another product" is really "fixing the defect where it lives"; DB-80's separation is *not* reducible to the no-path-dep rule — the profile, lockfile-discipline, and version/feature divergences (fact 5) are only expressible through separate workspace roots, and inside one workspace the no-cross-dep rule stops being structurally self-evident and drops to a pure assertion, while artifact-level coupling (single-version resolution, workspace-build feature unification) exists even with zero declared deps; and the DB-80 EP itself pre-answered this question by freezing placement behind "requires a new decision" — an advisory should need a far stronger cause than "the graph tool lacks a feature its owner can add," especially when (c) restores strictly more coverage (js/py at root) than the merge's rust-only fix would be credited for, at zero architectural cost, and keeps working when the next sibling workspace arrives.
