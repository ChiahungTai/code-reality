## Q3：設計草案（bridge 軸視角）

**D1｜attach face 泛化＋receipt 記 CR probe 狀態。**
做法：dispatch 時對 review-nature task 跑 review-engine 條 9 已定義的 <1s freshness probe，把結果（present/stale/unavailable/none＋serves 態）寫進 ledger 新欄位 `crProbe`；attach 段從「bridge 自家 review face 限定」放寬到「任何 review-nature 派工」。
為何現況失敗：attach 只在 review face（5/604）；ledger keys 無 CR 欄（jobs.json 實測）；78.3% 零注入＝無閘的直接後果。而 attach→使用的因果已有 muse ×75 實證。

**D2｜review-nature prompt 模板加「CR 面宣告段」，family 分流。**
做法：模板固定段按 carrier 發正確形態——codex 發 **CLI 字串**（`code-reality freshness --repo <root> --json`、`scip_refs <sym> --callers`、`graph_query detect_changes`，附 `[WARN]`+rg fallback）；glm/muse 才發 MCP 工具名。明文禁令：不得把 `mcp__plugin_code-reality__*` 發給 codex。
為何現況失敗：job-mubykur5-tnnybj 對 codex 發 MCP 名＝空頭支票；review-engine 硬性必含段只在 skill 不在派工路徑（78.3% 缺席）；23 個 test -f 劇場 job 證明無指引時 carrier 會自創最弱的替代儀式。

**D3｜WT 無 index 的 first-hop 處方（借用＋背景重建雙軌）。**
做法：probe 遇 `[cr:unavailable]` 時，attach face 自動解析主 worktree（`git worktree list`／common dir）以 `--repo <main>` 借用查詢，收據標 `serves=committed-baseline`（freshness 語義現成）；同時在 brief 附一行背景重建處方 `code-reality build --repo <wt>`（異步、不擋路——與 review-engine「禁阻塞式同步 rebuild」一致）。
為何現況失敗：db-55 的 `[FAIL]` 訊息自己寫了「先跑 graph_db build」但無人執行——把處方留給 carrier＝沒有處方；`.gitignore *` 使 WT 結構性絕緣（southchariot .code-reality/.gitignore 實文）。

**D4｜codex spawn 面診斷（先定位再修）。**
做法：bridge 側跑一次對照實驗——同一 repo 分別以現行 spawn face 與互動 codex（plugin 已載）各開一 job，diff `tools/list`；確認是 plugin 載入條件還是 `approval_mode="approve"` 在 non-interactive 面吞掉工具。若短期不可修，D2 的 CLI 分流即為 fallback，不必等。
為何現況失敗：config.toml 已啟用（marketplace＋enabled＋approval 設定俱全）但 193 job 零 surface——「已安裝」與「spawn 面可得」中間的斷點無人量測過。
